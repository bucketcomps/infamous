Real PS3 timing measured: our clock fix was the right shape, now with real numbers

From the volunteer's probe run (CECH-2001A, 4,136 OS timing measurements):

  • From the volunteer's probe run (CECH-2001A, 4,136 OS timing measurements):
  • usleep never wakes early (0 of 448), and overshoots by a steady +7–8 µs. A 3 µs sleep really takes about 10 µs, and there's no coarse scheduler tick.
  • A 250 ms lwcond wait times out at 250.014–250.023 ms, never early.
  • Timeout 0 means wait forever on all seven sync types.
  • A signalled thread wakes in 8–12 µs, or 3–8 µs if it has higher priority, and a higher-priority waiter runs before the signalling call even returns.
  • yield costs about 8 µs.
  • Our exact stall shape doesn't stall on hardware. A thread sleeping 3 µs at a time while the main thread waits 250 ms on an lwcond keeps waking about every 10 µs. That confirms today's fix: when everything is waiting, time must advance to the earliest wake-up.
  • Next: our runtime's hardware-clock mode is being changed to use these measured values instead of guesses. Every constant cites the exact probe records it came from.
  • the change merged: the carry and dcbz fixes across every CPU model are on main (no count change). The clock-fix and SPU-wake PR is queued for CI.

First real-PS3 run of probe v2: 6½ minutes, 1.1 GB of hardware data

What came back:

  • What came back:
  • the six PPU instruction sections, about 14.8 million results;
  • the PPU integer/flag addendum, 396,571 results;

  • The timebase measured again at 79.8 MHz.
  • One real bug in the probe, found on hardware: the SPU float test used dfceq, a double-precision compare that exists on IBM's later PowerXCell 8i chip but not on the PS3's Cell. The PS3's SPU stopped there, and RPCS3 independently flags the same instruction as invalid. That's a hardware fact worth knowing, but the probe shouldn't have included it, and the next version drops it. A knock-on SPU section also failed.

4,073 proven; what other PS3 recompilation projects teach us

Count: 4,073 / 21,054 functions proven (19.35%). the change merged one more: a big-endian word store at 0x00386028. An independent re-check decoded its bytes, re-ran the proof (it passes 4,000 test cases and an empty stub fails), and confirmed exactly one row was added.

  • Count: 4,073 / 21,054 functions proven (19.35%). the change merged one more: a big-endian word store at 0x00386028. An independent re-check decoded its bytes, re-ran the proof (it passes 4,000 test cases and an empty stub fails), and confirmed exactly one row was added.
  • Other PS3 recompilation projects, studied: Yakuza: Dead Souls, Uncharted 3, Dragon Ball Z Budokai HD and PS3Native.
  • Only the Yakuza project has a real graphics-chip-to-PC-GPU path. It claims gameplay at 19–30 FPS, which we have not verified.
  • The Uncharted 3 and DBZ projects draw only debug shapes so far.
  • None of them runs Sony's real SPU task system (SPURS) the way we do. They replace it, and Yakuza replaces the movie player with FFmpeg.
  • The most useful lesson for our current wall: Yakuza's runtime sends the "memory reservation lost" signal to waiting SPUs whenever the PPU writes to a reserved memory line. That's the signal our SPUs are waiting for, and a real-PS3 capture from CellGov confirms the PS3 does this. Our runtime is being checked for exactly that now.
  • Planned (not built): a bring-your-own-game installer. It reads your own disc or PSN copy, checks its version, extracts the assets, and lifts Sony's library code from your copy, so our downloads never contain anything copyrighted. Decryption keys are never shipped.

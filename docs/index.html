  • Count: 4,073 / 21,054 functions proven (19.35%). the change merged one more: a big-endian word store at 0x00386028. An independent re-check decoded its bytes, re-ran the proof (it passes 4,000 test cases and an empty stub fails), and confirmed exactly one row was added.
  • Other PS3 recompilation projects, studied: Yakuza: Dead Souls, Uncharted 3, Dragon Ball Z Budokai HD and PS3Native.
  • Only the Yakuza project has a real graphics-chip-to-PC-GPU path. It claims gameplay at 19–30 FPS, which we have not verified.
  • The Uncharted 3 and DBZ projects draw only debug shapes so far.
  • None of them runs Sony's real SPU task system (SPURS) the way we do. They replace it, and Yakuza replaces the movie player with FFmpeg.
  • The most useful lesson for our current wall: Yakuza's runtime sends the "memory reservation lost" signal to waiting SPUs whenever the PPU writes to a reserved memory line. That's the signal our SPUs are waiting for, and a real-PS3 capture from CellGov confirms the PS3 does this. Our runtime is being checked for exactly that now.
  • Planned (not built): a bring-your-own-game installer. It reads your own disc or PSN copy, checks its version, extracts the assets, and lifts Sony's library code from your copy, so our downloads never contain anything copyrighted. Decryption keys are never shipped.

Movie-stall fix accepted: the game's clock no longer freezes

Root cause: when every thread was asleep waiting on something, our runtime refused to move the game's clock forward to the next wake-up. A real PS3 just lets time pass. So time froze at 277.77 ms, even though a sleeping thread was due to wake 2.7 µs later, and our deadlock detector tripped at 233.78M instructions.

  • Root cause: when every thread was asleep waiting on something, our runtime refused to move the game's clock forward to the next wake-up. A real PS3 just lets time pass. So time froze at 277.77 ms, even though a sleeping thread was due to wake 2.7 µs later, and our deadlock detector tripped at 233.78M instructions.
  • Fix: when everything is parked, time now jumps to the earliest pending wake-up: a sleeper, a wait timeout, an SPU timer or a screen refresh. It never jumps past one, and never while any thread can run.
  • Measured: the corrected boot passed the old deadlock. Time keeps moving (287.63 ms reached), with 5 screen flips instead of 4, and the intro movie reached frame 3 of 353. It stopped only at the instruction cap we set for the test.
  • Independently reviewed (ACCEPT): taking the fix out reproduces the deadlock in the new test, 123 focused tests pass, and the default (non-hardware-clock) behaviour is byte-for-byte unchanged.
  • Next wall, a lead: at that cap, every SPU is parked waiting for a "memory reservation lost" signal on one address. On a real PS3, another core writing to that memory line sends it. A longer boot (to 600M instructions) is running now to see whether that signal ever arrives.
  • the change accepted by the lead: one more proven function (a word store at 0x00386028). The count goes to 4,073 / 21,054 (19.35%) once it merges.
  • New outside resources being used: RPCS3's ps3autotests (test programs with output recorded on a real PS3, now being run through our runtime), Sony's open-source Vector Math library (checking whether the game uses it), and CellGov (another team's deterministic PS3 interpreter with real-console test captures).

Carry-flag bug fixed in every CPU model; probe data now public

XER carry fixed everywhere. An audit found that our CPU models mishandled the carry flag on the add/subtract-with-carry and shift instructions. That covers the boot interpreter, the C interpreter, the native core and the C generator. On the boot interpreter's legacy path, addze ignored the carry, so the compiler's usual signed-divide pattern (srawi+addze, 203 places in the game) could be off by one on negative numbers. dcbz (clear a cache line) did nothing in three of the models. All of them now match the Power ISA exactly. An independent reviewer rebuilt the reference from the spec and found 0 mismatches.

  • Bink movie trigger is now source-backed. The controller script's "movie finished" trigger is tied to the BinkOpen/BinkClose sites decoded from the game binary. A reviewer at first rejected it on a misread address; we re-decoded the bytes, and it was accepted on re-review.

Safety review caught a black-screen bug in the extended probe; fixed build back in review

Extended probe RC1 rejected by our own safety review. It quit 46 µs after asking the PS3 whether video output was on. It never drew a single frame, so the volunteer would have seen only a black screen.

  • Extended probe RC1 rejected by our own safety review. It quit 46 µs after asking the PS3 whether video output was on. It never drew a single frame, so the volunteer would have seen only a black screen.
  • Cause: the open-source PS3 SDK's header says "video on" is 1, but the PS3 itself reports 0. The volunteer's real console proved it: its probe-v2 record shows videostate = 0 while running 1080p. RPCS3's code agrees.
  • Why the tests missed it: all 207 host tests passed, because none of them modelled that value. Only running the actual package caught it. This is why nothing goes to a volunteer without a run-through first.
  • Safety audit (on the binary) was clean:
  • no hypervisor calls; only normal system calls;
  • no save, ID, account, USB or network paths;
  • it writes one new file in /devhdd0/tmp;
  • audio was nulled.
  • RC2 is built with the fix (pkg 556e06dd…) and a test that pins the value. It is back in review, and this time the run must show the confirm screen and progress frames mid-run.
  • Also in review: the change (the lightweight condition-variable layout fix). Our float-store fix for the PS3 test suite went back for rework: its review found it flipped one proven function's result, because a NaN lost its minus sign.

Real PS3 timing measured: our clock fix was the right shape, now with real numbers

From the volunteer's probe run (CECH-2001A, 4,136 OS timing measurements):

  • From the volunteer's probe run (CECH-2001A, 4,136 OS timing measurements):
  • usleep never wakes early (0 of 448), and overshoots by a steady +7–8 µs. A 3 µs sleep really takes about 10 µs, and there's no coarse scheduler tick.
  • A 250 ms lwcond wait times out at 250.014–250.023 ms, never early.
  • Timeout 0 means wait forever on all seven sync types.
  • A signalled thread wakes in 8–12 µs, or 3–8 µs if it has higher priority, and a higher-priority waiter runs before the signalling call even returns.
  • yield costs about 8 µs.
  • Our exact stall shape doesn't stall on hardware. A thread sleeping 3 µs at a time while the main thread waits 250 ms on an lwcond keeps waking about every 10 µs. That confirms today's fix: when everything is waiting, time must advance to the earliest wake-up.
  • Next: our runtime's hardware-clock mode is being changed to use these measured values instead of guesses. Every constant cites the exact probe records it came from.
  • the change merged: the carry and dcbz fixes across every CPU model are on main (no count change). The clock-fix and SPU-wake PR is queued for CI.

What came back:

  • What came back:

  • One real bug in the probe, found on hardware: the SPU float test used dfceq, a double-precision compare that exists on IBM's later PowerXCell 8i chip but not on the PS3's Cell.
